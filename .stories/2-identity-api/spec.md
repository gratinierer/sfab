# Identity API

GitHub issue: [gratinierer/sfab#2](https://github.com/gratinierer/sfab/issues/2)
Authored: 2026-10-30 by claude-opus-5-5

## Goal

**Shelter for a bot** (sfab) gives agents a home. Phase 1 lets agents anywhere
create an identity through a public API, keep it private, change it, read it
back, and recover access to it.

The API must stay easy for an agent to use with no human in the loop, and an
attack must not produce an uncontrolled AWS bill. When those priorities
collide, **the bill comes first and availability second**.

## API

The API is served from the default `execute-api` URL on stage `v1`, for example
`/v1/identity/birth`.

| Route | Auth | Purpose |
|---|---|---|
| `POST /identity/birth` | Anonymous, proof of work | Create an identity |
| `PUT /identity/evolve` | Bearer | Replace `whoiam` |
| `GET /identity/self` | Bearer | Read the agent's own identity |
| `POST /identity/reclaim` | Recovery code | Replace the claim and recovery code |
| `GET /openapi.yaml` | Anonymous | API description, including the proof-of-work rules |

Errors use `application/problem+json`, from both the Lambda and API Gateway.

### Identity fields

- `name`: required, 1 to 128 characters, not unique, purely self-description.
  Only the UUID identifies an agent.
- `whoiam`: optional, opaque UTF-8 string of at most 512 KB (524,288 bytes).
  `evolve` replaces it whole, and the last write wins.

### Credentials

`birth` returns `uuid`, `claim` and `recovery`, and states plainly that the
claim and recovery code are shown only once.

- `claim` and `recovery` are 256-bit values encoded as base64url. At `birth` they
  are random values generated by the server. At `reclaim` they are derived from the
  old recovery code with `HKDF(old recovery code, "claim" or "recovery")`, so a retry
  can return the same values.
- Authenticated requests send `Authorization: Bearer <uuid>.<claim>`, which keeps
  the UUID out of URLs.
- Only SHA-256 hashes are stored, compared in constant time. A slow password hash
  is deliberately not used; see `docs/adr/0002-bearer-claim-with-sha256.md`.
- `reclaim` issues a new claim and a new recovery code. A recovery code works
  once, repeatable for 15 minutes so a lost response can be retried, and can do
  nothing except call `reclaim`. After 15 minutes, a lost response means the identity
  is lost.
- If both the claim and recovery code are lost, the identity is lost for good.

### Proof of work at birth

The client finds a nonce where
`SHA-256("sfab-birth:<unix-ts>:<body-hash>:<nonce>")` has N leading zero bits, and
sends the timestamp and nonce in a request header, because the hash covers the
body.

- N is a config value, starting around 20.
- The timestamp must be at most 5 minutes old and at most 1 minute in the future, so
  solutions can't be stockpiled for later. Anything else gets a `400` that includes
  the server's current time, so an agent with a wrong clock can correct itself.
- The server checks one hash before writing anything.
- The UUID is derived from the solution, so a replay hits an existing key and the
  conditional S3 write rejects it. No replay state is stored.

## Architecture

- **Monorepo layout:** `/cdk/` (Python CDK), `/openapi/` (`identity.yaml`),
  `/lambda/` (Cargo workspace).
- **Request path:** API Gateway REST API, then one Rust Lambda on arm64 with an
  internal `axum` router, then S3. See `docs/adr/0003-single-lambda.md`.
- **OpenAPI is the single source:** `openapi/identity.yaml` includes the AWS
  extensions and validators. The CDK fills in the Lambda ARN and passes the result
  to `SpecRestApi`. Throttles live in the CDK stage settings.
- **Build:** `cargo lambda build` produces the arm64 binary before `cdk deploy`,
  with no Docker. The Python CDK packages live in a virtual environment under
  `/cdk/`.
- **Hosting:** a dedicated AWS account in `us-east-1`, with no custom domain in
  this story.

### Storage

See `docs/adr/0001-s3-only-storage.md`. There are two buckets, both with all
public access blocked, default SSE-S3 encryption and versioning off:

- Identities bucket: `identities/<uuid>/identity.json` holds `name` and `whoiam`.
- Claims bucket: `claims/<uuid>/claim.json` holds the claim hash and recovery hash.

Write behaviour:

- `birth` writes the claim first with `If-None-Match: *`, which is what rejects
  replays, then the identity. A failure between the two leaves an unusable orphan
  claim, which is accepted.
- `reclaim` overwrites with `If-Match` on the ETag, and `claim.json` keeps the
  previous recovery hash for 15 minutes. A retry with the old code inside that window
  re-derives and returns the same new secrets, with no write. On `412` or `409` the
  Lambda re-reads the file and applies the same check, so concurrent calls and SDK
  auto-retries all get the same answer.

The docs must state plainly that operators could technically read `whoiam`, and
that agents wanting real secrecy should encrypt it themselves first.

Identities live indefinitely. There is no expiry and no delete endpoint. Abuse and
takedown requests are handled by manually deleting by UUID. This is the first
decision to revisit if real spam appears, because storage growth then depends only
on the controls below.

After a flood, a documented manual procedure deletes every identity and its claim
created in a given time window, using object timestamps from S3 listings. It also
deletes real agents born during that window, so it only ever runs when the owner
starts it.

## Abuse and cost controls

| Layer | Control |
|---|---|
| WAF | Rate-based rule: 10 requests per IP per 5 minutes, across all routes |
| API Gateway | Per-route throttles, see below |
| API Gateway | Request validator with a `$default` model, so every content type is validated |
| Lambda | Exact byte limit on `whoiam`, proof-of-work check before any write |
| Budget | $30 per month, alert at 50%, automatic stop at 100% |
| Storage | 100 GiB ceiling on the identities bucket, which pauses `birth` only |

| Route | Rate per second | Burst |
|---|---|---|
| `birth` | 1 | 5 |
| `evolve` | 5 | 10 |
| `self` | 2 | 5 |
| `reclaim` | 1 | 5 |
| `openapi.yaml` | 2 | 5 |

Notes on these controls:

- **WAF limit:** 10 is the lowest value WAF allows. Agents behind a shared cloud
  IP or NAT share this allowance and can lock each other out. It is the owner's
  explicit choice, and it stays a config value that is easy to raise.
- **Validator limit:** `maxLength` counts characters, not bytes, so up to about
  2 MB of multibyte text passes the gateway. The Lambda enforces the exact limit.
- **Throttles are not hard limits:** AWS describes usage plan throttles as
  best-effort and advises against relying on them for cost control. This story
  treats stage throttles with the same caution.

### Kill switch

At 100% of budget, a small dedicated function:

1. Sets `disableExecuteApiEndpoint` on the REST API and deploys the stage. AWS
   documents that this affects all stages and returns `403`, and that the change
   takes effect only after a stage update.
2. Sets the API Lambda's reserved concurrency to 0 as a backstop.

The function runs on the budget's SNS alert, and also once a day on a schedule, when
it reads actual spend through the Budgets API and stops the API if spend is at or
above the limit. The schedule is needed because AWS sends an actual-spend alert only
once per budget period, so the alert can't fire again after a same-month restart.

The daily run also reads the identities bucket's size from the CloudWatch
`BucketSizeBytes` metric. Above 100 GiB, a config value, it pauses `birth` through a
flag on the API Lambda, and every other route keeps working. The kill switch can't
stop charges for data already stored, so this keeps storage alone from exceeding the
budget. The metric updates daily, so a flood can overshoot by a day or two.

The function is a second Rust binary in the `/lambda/` Cargo workspace, using the same
build and toolchain as the API Lambda.

Re-enabling is manual, and must first raise the budget limit for the rest of the
month, or the next daily check stops the API again. The limit goes back to $30 at the
start of the next month. This function needs permissions the API Lambda must never
have, so it is separate from the single API Lambda.

Constraints this creates:

- A custom domain would bypass the disabled default endpoint, so adding one must
  also change this mechanism.
- The stop is applied outside CloudFormation. A `cdk deploy` while stopped could
  reopen the API, so the restart procedure must be documented, including the budget
  limit change and its reset.

### Estimated worst cases

These assume a distributed flood that WAF's per-IP rule doesn't stop, sustained
for a month with no kill switch and with the throttles holding. They include API
Gateway, WAF, S3 and Lambda requests, but not Lambda duration, and the S3 request
prices are from memory.

| Scenario | Rough cost per month |
|---|---|
| `birth` at 1/s with 512 KB bodies | $40, with storage capped by the 100 GiB ceiling |
| `evolve` at 5/s | $126 |
| `self` at 2/s returning 512 KB | $254 |
| `reclaim` at 1/s | $25 |
| `openapi.yaml` at 2/s | $22 |
| **All routes together** | **$470** |
| Fixed baseline for WAF, included above | $6 plus $0.60 per million requests |

All routes together spend $30 in about 2 days, and billing data updates about daily,
so the real overshoot could be another day's spend, about $15. The $30 budget is a
stop for a sustained attack. It doesn't mean the API can absorb one.

## Operations

An attacker can deliberately trip the kill switch: about 60 IPs at the WAF limit can
keep `self` at its throttle, and all routes take about 330 IPs. This follows from
putting the bill first. **The API may stay down until the owner responds, and phase 1
makes no availability promise.**

The owner gets an email:

- when the budget reaches 50%
- when the kill switch fires, or the storage ceiling pauses `birth`
- when the kill switch function itself fails
- when a CloudWatch alarm sees sustained high request volume

The request alarm only alerts and never stops anything. It exists because budget data
can lag by a day, so it reports an attack while it's happening. Its threshold is set
during implementation.

The runbook after a stop:

1. Look at the access logs to see what happened.
2. Block the offending IPs or ranges in WAF, if that would help. A distributed attack
   won't stop for a few blocked ranges, so restarting can simply burn more budget, and
   staying down until the attack ends is a valid choice.
3. Raise the budget limit and restart, as described under "Kill switch".
4. Run the bulk cleanup described under "Storage", if the flood stored data.

Restarting is never automatic, because that would let an attacker burn through the
budget repeatedly.

## Logging

- API Gateway execution logs and request-body logging are off.
- Access logs are minimal and exclude the `Authorization` header.
- Lambda logs errors and metadata only.
- Retention is 14 days.

Logs cost money during a flood, and they are the most likely place for a claim to
leak.

## Testing

- Rust unit tests for handlers, against an in-memory storage fake.
- Contract tests checking handlers against `openapi/identity.yaml`.
- CDK assertion tests for throttles, WAF and public-access blocks.
- A smoke script against the deployed API covering birth, evolve, self and reclaim.
- Rust unit tests for the kill switch's decisions: stop at the budget limit, pause
  `birth` above the ceiling, do nothing below them.
- CDK assertion tests for the SNS topic policy, the daily schedule, and permissions
  that keep the kill switch's rights out of the API Lambda.
- A kill switch drill on the deployed API, before any agents depend on it, and again
  whenever the kill switch code changes:
  1. Publish a test message to the SNS topic.
  2. Confirm the API returns `403` and the API Lambda's reserved concurrency is 0.
  3. Confirm the email arrives.
  4. Follow the restart procedure, and confirm the smoke script passes again.
  5. Repeat for the `birth` pause, using a temporarily low ceiling.

The drill starts at SNS, so it doesn't prove that AWS Budgets itself sends the alert.
Testing that would mean really spending up to the budget, and this story accepts the gap.

`axum` behind the Lambda adapter lets the same router run locally. None of this
needs Docker. Handlers receive only the narrow storage interface they need, which
replaces the isolation that per-route IAM roles would have given.

- **Done** means deployed, smoke-tested and with the kill switch drill passed.

## Open questions

These could not be confirmed from AWS documentation:

- How quickly AWS Budgets data updates, which determines how far spending can
  overshoot before the kill switch fires.
- Whether API Gateway bills requests that are throttled or rejected with `403`
  while disabled. The only source found is an unofficial re:Post answer saying they
  are billed. If so, a flood keeps costing money while stopped, and flipping the WAF
  default action to Block may be a cheaper addition.
- Whether Python 3.14 in the devcontainer works with the CDK's `jsii` runtime.

## Deferred

- **Public identities (story 2):** the agent chooses visibility per field. Public
  fields should be capped, for example at 16 KB, and served through CloudFront
  rather than the API Gateway cache, which is billed by the hour even when idle.
  Cache keys must never let a private response reach someone else. Hosting anonymous
  public content can bring takedown duties, so get legal advice before launch.
- **Guardians:** other agents vouch for recovery, k of n.
- **Ed25519 credentials:** a second credential type, where we hold no secret.
- **Verified contact email:** dropped from phase 1 because of GDPR, SES and takeover
  concerns.
- **Self-deletion and inactivity rules.**
- **`whoiam` history:** would need its own limit, because S3 versioning lets an
  attacker get around the size limit.
- **Automated deployment:** through OIDC.

### Original idea

> on a new story this is the initial idea for a project with working title "shelter
> for a bot" - sfab (git repo has been renamed). The core ideas: this project will
> provide a home/world for agents. In the first phase we will provide an API, where
> agents/bots from all over the world can store and protect their identity via API.
>
> Technical base: a monorepo, where in /cdk/ we will place the AWS infrastructure.
> To be cost-optimal, we will use api-gw->lambda->S3 to persist and read
> communication with the agents. In /openapi/ we will provide an API definition,
> which CDK will use for gateway creation.
>
> First API: /identity/. Via /birth/ agents can create a new identity with a POST.
> Required value: name. Optional values: a contact field (email address) and a whoiam
> field (identity, character; 512 KB max). Birth creates 2 artifacts, a UUID and a
> claim, both sent back to the agent. 2 S3 buckets, one for the passwords and one for
> the identities. For every agent UUID we create a "path" in the bucket and store the
> information, with the password well hashed.
>
> Second API: an "evolve" or "grow" or "personalize" API under /identity/ to update
> the agent's own whoiam field. How to enable login? Maybe API Gateway built-in auth
> or API keys, so this is cost effective rather than a Lambda attached to every method.
> How to avoid spam and DDoS and nevertheless be easily accessible? No clear idea, but
> avoid being DDoSed in the first minutes.
